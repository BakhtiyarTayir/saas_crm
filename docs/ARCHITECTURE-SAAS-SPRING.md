## 0. Контекст

**Что строим.** Мультиарендную (multi-tenant) SaaS CRM для учебных центров: один экземпляр системы, много центров-клиентов, данные каждого центра полностью изолированы от остальных.

**Рынок.** Узбекистан, дальше, возможно, Центральная Азия. Языки интерфейса — узбекский (латиница) и русский. У многих учеников нет почты, основной идентификатор — телефон и Telegram. Оплаты — наличные, карта, Payme, Click, перевод. SMS — Eskiz.

**Кто строит.** Один разработчик. Отсюда выбор модульного монолита и минимума инфраструктуры.

**Опыт предыдущего продукта.** best-direction — CRM + LMS одного центра на Next.js. Работает в проде и содержит проверенную доменную логику (начисления с заморозкой закрытых месяцев, посещаемость с заменами преподавателей). Аудит показал, что главные проблемы были не в логике, а в том, как проверялись права и где жили правила. Раздел 15 — прямой перенос этих уроков.

### Главный риск продукта

**Утечка данных между центрами.** Один забытый фильтр по арендатору — и центр А видит учеников, телефоны и оплаты центра Б. Для SaaS это конец продукта, а не баг. Вся архитектура ниже подчинена тому, чтобы такая утечка требовала осознанного действия, а не забывчивости.

## 1. Принципы

1. **Изоляция арендаторов структурная, в два независимых слоя:** ORM и база данных. Ни один слой не полагается на дисциплину разработчика.
2. **Доступ запрещён по умолчанию.** Эндпоинт без явного правила доступа не проходит сборку.
3. **Правила живут только на сервере.** Фронтенд прячет кнопки для удобства, но ничего не защищает.
4. **Каждый вход валидируется на сервере.** Сущности JPA наружу не отдаются, только DTO.
5. **Деньги — только через журнал.** Проведённая денежная запись не редактируется; исправление — сторнирующая запись.
6. **Долгое и внешнее — через outbox и фоновые задачи.** Ни одна отправка SMS, Telegram или email не делается внутри HTTP-запроса.
7. **Модульный монолит.** Границы модулей проверяются тестом. Никаких микросервисов, пока не появится измеримая причина.
8. **Бэкапы, мониторинг и тесты в CI — с первого дня**, до первой бизнес-функции.

## 3. Модули

Модульный монолит на Spring Modulith: пакеты верхнего уровня под корневым пакетом — модули. Всё во вложенном пакете `internal` недоступно другим модулям; тест `ApplicationModules.of(...).verify()` падает при нарушении.

```
uz.<company>.crm
├── CrmApplication.java
├── shared/            Money, TenantScopedEntity, ProblemDetail-фабрики, общие типы
├── tenancy/           Tenant, Branch, TenantContext, резолвер арендатора, RLS
├── identity/          User, Membership, Role, Permission, сессии, вход (телефон, Telegram, пароль)
├── audit/             журнал действий
├── staff/             сотрудники центра, преподаватели
├── students/          ученики, родители, связи родитель–ученик
├── courses/           курсы, группы, расписание
├── enrollment/        зачисление ученика в группу, переводы, паузы, уход
├── attendance/        занятия, отметки учеников и преподавателей, замены
├── billing/           начисления ученикам, закрытие месяцев, скидки
├── payments/          приём оплат, кассы, Payme/Click
├── notifications/     SMS (Eskiz), Telegram, email; шаблоны; outbox
├── leads/             заявки, воронка
├── reporting/         отчёты, выгрузки
└── platform/          подписка центров на SaaS, тарифы, лимиты, суперадмин платформы
```

**Два разных «биллинга» — не путать в именах:**
- `billing` — центр начисляет **своим ученикам** плату за обучение.
- `platform` — **платформа** выставляет центру плату за подписку на SaaS.

Модули общаются через публичные сервисы модуля или события (`ApplicationEventPublisher` + `@ApplicationModuleListener`). Прямой доступ к репозиториям чужого модуля запрещён.

## 4. Мультиарендность

### 4.1. Модель

**Одна БД, одна схема, колонка `tenant_id` во всех таблицах с данными центра.**

Почему не схема на арендатора и не БД на арендатора: миграция N схем идёт N раз и падает посередине, пул соединений размножается, сводная аналитика платформы превращается в сборку по схемам. Строковая изоляция с RLS даёт сопоставимую защиту без этих затрат. Выделенная БД для крупного клиента при необходимости добавляется позже маршрутизацией `DataSource`, не с первого дня.

**`Tenant`** — организация (учебный центр или сеть).
**`Branch`** — филиал внутри арендатора. Сети учебных центров с несколькими филиалами — обычное дело. Права сотрудника могут быть ограничены филиалом (раздел 5.3).

Таблицы платформы без `tenant_id`: `tenant`, `user`, `membership`, тарифы и подписки платформы, справочники платформы.

### 4.2. Слой 1 — ORM

```java
@MappedSuperclass
public abstract class TenantScopedEntity {
    @TenantId
    @Column(name = "tenant_id", nullable = false, updatable = false)
    private UUID tenantId;
}
```

Все сущности с данными центра наследуют `TenantScopedEntity`. Hibernate сам добавляет условие по арендатору в запросы и сам проставляет `tenant_id` при вставке. Текущий арендатор Hibernate получает из `CurrentTenantIdentifierResolver`, который читает `TenantContext`.

**Тест ArchUnit:** каждая `@Entity` в модулях с данными центра наследует `TenantScopedEntity`, кроме явного списка таблиц платформы.

### 4.3. Слой 2 — Row-Level Security в Postgres

Слой ORM не видит нативный SQL, `JdbcTemplate`, отчётные запросы и ошибки в JPQL. RLS ловит всё это на уровне базы.

```sql
ALTER TABLE student ENABLE ROW LEVEL SECURITY;
ALTER TABLE student FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON student
  USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
```

Обязательные детали, каждая — отдельная дыра, если её пропустить:

- **`FORCE ROW LEVEL SECURITY`.** Без него владелец таблицы обходит политики.
- **Два пользователя БД.** Миграции Flyway — под владельцем таблиц. Приложение — под отдельным пользователем без `BYPASSRLS`, который таблицами не владеет.
- **`WITH CHECK`.** Без него запись с чужим `tenant_id` пройдёт, хотя прочитать её потом будет нельзя.
- **`current_setting(..., true)` + `NULLIF`.** Если контекст не выставлен, условие даёт `NULL` → ноль строк. Система отказывает закрыто, а не падает и не отдаёт всё.
- **Сброс контекста при возврате соединения в пул.** HikariCP переиспользует соединения. Значение, выставленное для одного запроса и не сброшенное, достанется следующему запросу другого арендатора.

**Реализация выставления контекста** — одно из двух, выбрать при создании каркаса:
- транзакционно-локально: `SELECT set_config('app.tenant_id', ?, true)` сразу после начала каждой транзакции (значение исчезает при COMMIT/ROLLBACK сам);
- обёртка над `DataSource`: `set_config('app.tenant_id', ?, false)` при выдаче соединения и `RESET app.tenant_id` при возврате.

Первый вариант надёжнее, если найдётся корректная точка подключения после `BEGIN` для используемого менеджера транзакций.

**Тесты RLS (обязательные):**
1. Запрос без выставленного контекста возвращает 0 строк.
2. После возврата соединения в пул следующий запрос из другого потока без контекста не видит данных предыдущего арендатора.
3. Нативный SQL-запрос от имени арендатора A не видит строк арендатора B.
4. Вставка строки с чужим `tenant_id` отклоняется.

### 4.4. Откуда берётся текущий арендатор

1. Пользователь аутентифицирован → в сессии хранится `activeTenantId` (выбранный центр среди его членств).
2. Фильтр после аутентификации проверяет, что `Membership(user, activeTenantId)` существует и активно (кэш на 30 секунд), и выставляет `TenantContext`.
3. Нет активного членства → 403, контекст не выставляется.

**Поддомен (`center1.app.uz`) или путь используются только для удобства** — чтобы предложить нужный центр при входе. Доверять им как источнику арендатора нельзя: сервер всегда сверяет с членством.

### 4.5. Где утечки случаются на практике

| Место | Защита |
|---|---|
| Фоновая задача | Полезная нагрузка задачи содержит `tenantId`; обёртка исполнителя выставляет `TenantContext` и контекст RLS до вызова обработчика и очищает после. Задачи без `tenantId` — только платформенные, из явного списка. |
| Кэш | Ключ кэша всегда содержит `tenant_id`. Обёртка над кэшем добавляет его сама. |
| Выгрузки и отчёты | Идут через те же сервисы с тем же контекстом; RLS страхует нативные запросы. |
| Уникальные индексы | Все бизнес-уникальности включают `tenant_id` (раздел 12). |
| Файлы | Ключ объекта в хранилище начинается с `tenant_id`; presigned URL выдаётся только после проверки доступа. |
| Логи | `tenant_id` в MDC; данные чужого арендатора в сообщения об ошибках не попадают. |
| Суперадмин платформы | Отдельный пул соединений под пользователем БД с `BYPASSRLS`, доступный только модулю `platform`. Каждое действие — в журнал аудита. Вход «от имени центра» — явный, ограниченный по времени, с записью в журнал. |

### 4.6. Жизненный цикл арендатора

- **Создание:** самостоятельная регистрация центра → `Tenant`, первый `Branch`, `Membership` владельца с ролью OWNER, пробный тариф.
- **Приостановка:** за неоплату подписки — только чтение; данные не удаляются.
- **Выгрузка:** центр может выгрузить все свои данные (ученики, группы, посещаемость, начисления, оплаты).
- **Удаление:** по запросу центра — после периода удержания, фоновой задачей, с записью в журнал платформы.

## 5. Пользователи, вход, права

### 5.1. Модель

```
User (глобальный)            Membership                     Tenant
─────────────────            ──────────                     ──────
id                           user_id    ──▶ User            id
phone  (unique)              tenant_id  ──▶ Tenant          name
email  (unique, nullable)    role_id    ──▶ Role            timezone
telegram_id (unique, null)   branch_ids (null = все)        default_locale
password_hash (nullable)     status (ACTIVE/SUSPENDED)      status
status                       created_at
```

- **Роль хранится в членстве, а не в пользователе.** Преподаватель ведёт группы в двух центрах; родитель, у которого дети в разных центрах, — один человек с одним логином.
- **Телефон — основной идентификатор.** Почта необязательна.
- **Ученик может не иметь логина вообще.** Карточка ученика (`Student`) — данные центра с `tenant_id`; привязка к `User` появляется, только когда ученику или родителю выдают доступ в кабинет.

### 5.2. Вход и сессии

- Способы входа: одноразовый код по SMS на телефон, Telegram (виджет с проверкой подписи или подтверждение в боте), пароль.
- **Серверные сессии** (Spring Session JDBC), кука `HttpOnly`, `Secure`, `SameSite=Lax`.
- При деактивации пользователя, сбросе пароля и по кнопке «выйти на всех устройствах» удаляются **все** его сессии (`FindByIndexNameSessionRepository`).
- Отзыв членства в одном центре действует в пределах TTL кэша членства (30 секунд), без выхода из системы.
- Rate limiting (Bucket4j): запрос OTP — по телефону и по IP; проверка OTP — ограниченное число попыток на код; вход по паролю — по логину и по IP.
- Ответ на запрос сброса пароля и OTP одинаковый для существующего и несуществующего пользователя.

**Keycloak не использовать на старте:** отдельная JVM и сотни мегабайт памяти ради того, что Spring Security делает сам. Вернуться к вопросу, если крупный клиент потребует SSO.

### 5.3. Права

**Роли раскладываются на права.** Проверки в коде — только по правам, никогда по названию роли.

```
students.read   students.write   attendance.mark   attendance.edit_past
payments.create payments.void    billing.close_month  reports.finance
groups.manage   staff.manage     settings.manage   notifications.send
```

- Системные роли на старте: OWNER, ADMIN, MANAGER, CASHIER, TEACHER, PARENT, STUDENT.
- Центр может создать свою роль из набора прав (кассир, ресепшн, методист) — центры попросят это первым делом.
- Членство может быть ограничено филиалами (`branch_ids`): кассир филиала видит оплаты только своего филиала.

**Проверка на уровне метода:**

```java
@PreAuthorize("hasAuthority('payments.create')")
@PostMapping("/payments")
public PaymentResponse create(@Valid @RequestBody CreatePaymentRequest request) { ... }
```

**Объектный уровень** (преподаватель — только свои группы, родитель — только свои дети, кассир — только свой филиал) проверяется в сервисе модуля через политику, а выборки строятся через `Specification` с условиями этой политики. Ручных `if (role == ...)` в контроллерах нет.

### 5.4. Запрет по умолчанию — тестом

```java
@AnalyzeClasses(packages = "uz.<company>.crm")
class SecurityArchitectureTest {

    @ArchTest
    static final ArchRule every_endpoint_declares_access =
        methods().that().areDeclaredInClassesThat().areAnnotatedWith(RestController.class)
            .and().arePublic()
            .should().beAnnotatedWith(PreAuthorize.class)
            .orShould().beAnnotatedWith(PublicEndpoint.class);
}
```

`@PublicEndpoint` — своя аннотация для заведомо публичных маршрутов (вход, публичная форма заявки, вебхуки платёжных систем с собственной проверкой подписи). Список публичных маршрутов короткий и проверяется на ревью.

Дополнительно в `SecurityFilterChain`: `anyRequest().authenticated()` в конце цепочки. Публичные маршруты перечисляются явно.

## 6. Ядро доменной модели

Все сущности ниже — с `tenant_id`.

```
Branch ──< Group >── Course
             │
             ├──< GroupSchedule (день недели, время, аудитория, преподаватель)
             ├──< Lesson (конкретное занятие на дату; создаётся из расписания)
             │       ├── teacher (фактический, может отличаться — замена)
             │       └──< AttendanceMark (ученик, статус, комментарий)
             │
             └──< Enrollment >── Student ──< ParentLink >── Parent
                     │
                     ├── starts_on, ends_on, pause периоды
                     ├── price_override, discount
                     └──< Charge (журнал начислений)

Student ──< Payment ──< PaymentAllocation >── Charge
```

- **Посещаемость привязана к конкретному занятию группы**, у занятия свой фактический преподаватель. Правило «отмечать может ведущий занятия, преподаватель группы или администратор» из `best-direction/src/lib/attendance-access.ts` переносится как политика модуля `attendance`.
- **Перевод ученика между группами** — закрытие одного `Enrollment` и открытие другого, а не правка `group_id`: иначе история начислений и посещаемости переписывается задним числом.
- **Пауза** — отдельный период внутри `Enrollment`, начисления за него не идут.

## 7. Деньги и время

### 7.1. Деньги

- Сумма — `BigDecimal` в Java, `numeric(18,2)` в Postgres. Никогда `double` или `float`.
- Объект-значение `Money(amount, currency)`. Валюта хранится у арендатора; на старте UZS.
- **Правило округления — настройка арендатора:** до сума, до 100, до 1000. Пропорциональные начисления за неполный месяц округляются по этому правилу явно указанным `RoundingMode`, а не «как получится».

### 7.2. Время

- Моменты — `Instant` / `timestamptz`.
- Календарные даты — `LocalDate` / `date`. Месяцы — `YearMonth`.
- **Часовой пояс — у арендатора** (по умолчанию `Asia/Tashkent`). Границы дня и месяца, «сегодня», «месяц закрыт» считаются в часовом поясе арендатора, а не сервера и не UTC.

В best-direction календарные даты хранились полднем UTC, а месяцы — строками `"YYYY-MM"`, чтобы обойти сдвиг даты на сутки. В Java для этого есть нормальные типы, обходные приёмы не нужны.

## 8. Начисления ученикам (модуль billing)

Переносится идея из `best-direction/src/lib/billing.ts` и `billing-ledger.ts` — она проверена в проде и верна по сути.

- **Полный месяц** стоит цену. **Неполный** (первый, последний, с паузой) начисляется пропорционально **занятиям по расписанию группы**, а не календарным дням; если расписания нет — по дням.
- **Приоритет цены:** индивидуальная цена ученика → цена группы → цена курса.
- **Ручная сумма за первый неполный месяц** важнее формулы.
- **Журнал `Charge` только дописывается.** Каждая запись хранит месяц, сумму, основание (full / lessons / days / manual), число занятий всего и оплачиваемых, использованную цену.
- **Закрытие месяца.** Текущий месяц считается формулой и может меняться. Прошедший месяц фиксируется записями в журнале и больше не пересчитывается — изменение цены в октябре не переписывает долг за сентябрь. В отличие от best-direction, где месяц замораживался лениво при первом просмотре, здесь закрытие — плановая задача в первый день месяца по часовому поясу арендатора, плюс принудительная заморозка перед любым изменением цены, дат или группы.
- **Исправление закрытого месяца** — сторнирующая запись плюс новая, с комментарием и записью в журнал аудита. Право `billing.close_month` / отдельное право на корректировку.
- **Долг** = сумма начислений − сумма распределённых оплат, считается запросом по журналу, а не хранится полем.

**Тесты модуля** переносят проверки из `best-direction/scripts/check-billing.ts` и `check-billing-db.ts`: пропорция по занятиям, приход после последнего занятия месяца, приоритет цен, неизменность закрытого месяца после смены цены, переход записи между бесплатной и платной.

## 9. Оплаты (модуль payments)

- Оплата создаётся с **ключом идемпотентности** (заголовок `Idempotency-Key`, уникальный индекс `(tenant_id, idempotency_key)`) — двойной клик кассира не создаёт два платежа.
- Проведённая оплата не редактируется и не удаляется. Ошибочная — аннулируется (`void`) отдельной операцией с причиной и правом `payments.void`.
- Оплата распределяется по начислениям (`PaymentAllocation`). Нераспределённый остаток — аванс.
- **Payme / Click:** вебхук помечен `@PublicEndpoint`, подпись или авторизация проверяются строго по документации провайдера до любых действий. Идемпотентность по id транзакции провайдера — уникальный индекс. Арендатор определяется по учётным данным мерчанта, а не по полю из тела запроса.
- Запись в журнал аудита — в той же транзакции, что и оплата.

## 10. Уведомления и фоновые задачи

### 10.1. Outbox

Бизнес-операция и намерение отправить уведомление фиксируются в одной транзакции. Spring Modulith сохраняет событие в реестре публикаций; обработчик `@ApplicationModuleListener` выполняется после коммита. При сбое событие остаётся незавершённым и повторяется.

Итог: SMS не уходит, если операция откатилась, и не теряется, если операция прошла.

### 10.2. Задачи

db-scheduler или JobRunr на Postgres:
- закрытие месяца по часовому поясу каждого арендатора;
- массовые рассылки (разбиваются на части, учитывают лимиты Eskiz);
- напоминания о долге и о занятии;
- выгрузки и тяжёлые отчёты;
- удаление данных арендатора по истечении срока.

Каждая задача несёт `tenantId` (раздел 4.5).

### 10.3. Каналы

- **SMS (Eskiz):** токен хранится в БД, обновляется заранее. Только согласованные шаблоны. Журнал каждого сообщения с ценой и числом частей. Callback о статусе доставки — с секретом в пути.
- **Telegram:** один бот платформы; привязка чата к `User` через одноразовый код с ограниченным сроком жизни в отдельной таблице (не перезаписывать существующую привязку — ошибка 2.8 из аудита). Webhook отвечает 200 даже при ошибке обработчика, иначе Telegram повторяет апдейт бесконечно.
- **Email:** вторичный канал.

Шаблоны уведомлений — на двух языках, язык берётся у получателя, иначе у арендатора.

## 11. API и фронтенд

### 11.1. API

- REST, префикс `/api/v1`.
- Запросы и ответы — record-классы DTO с `@Valid`. Сущности JPA наружу не отдаются.
- **Пагинация обязательна** для всех списков. Максимальный размер страницы ограничен на сервере.
- Ошибки — `ProblemDetail`. Поле с ключом перевода, текст переводит фронтенд.
- **Недоступный по правам объект — 404, а не 403**, чтобы не подтверждать существование чужого id.
- Строки ограничены по длине, массивы — по размеру, числа — по диапазону.
- OpenAPI публикуется springdoc и является контрактом для фронтенда.

### 11.2. CSRF

Сессия в куке → CSRF-защита Spring Security **включена**. Для SPA: `CookieCsrfTokenRepository` (кука читается JavaScript) и обработчик токена для SPA по документации Spring Security; фронтенд отправляет токен заголовком `X-XSRF-TOKEN`.

### 11.3. Фронтенд

- SPA на React + Vite + TypeScript, раздаётся статикой через Caddy **на том же домене**, что и `/api` — кука сессии без CORS.
- TanStack Query для данных, TanStack Router для маршрутов, shadcn/ui + Tailwind.
- Клиент API генерируется orval из OpenAPI; сгенерированный код руками не редактируется.
- Права в интерфейсе (скрыть кнопку, пункт меню) — только удобство. Сервер проверяет всё сам.
- Переводы uz / ru.

```
web/src/
├── app/            роутер, провайдеры, layout
├── features/
│   ├── students/
│   ├── groups/
│   ├── attendance/
│   ├── billing/
│   ├── payments/
│   └── ...
└── shared/
    ├── api/        сгенерированный клиент — не редактировать
    ├── ui/         компоненты shadcn
    ├── auth/       текущий пользователь, активный центр, права для UI
    └── i18n/
```

**Почему не Next.js:** CRM находится за логином, SSR и SEO ей не нужны, а серверный слой Next.js стал бы вторым местом, где можно разместить бизнес-правило. Правила должны жить только в Spring.

## 12. Данные и миграции

- **Flyway**, чистый SQL. RLS-политики создаются в той же миграции, что и таблица.
- **Каждая таблица с данными центра:** `tenant_id uuid NOT NULL`, включена и форсирована RLS, индексы начинаются с `tenant_id`.
- **Все бизнес-уникальности включают `tenant_id`:** `UNIQUE (tenant_id, slug)`, `UNIQUE (tenant_id, name)` для групп и т.д. В best-direction `Course.slug` и `User.number` уникальны глобально — в SaaS это означало бы, что центры отнимают друг у друга названия.
- **Нумерация внутри центра** («Ученик №1» у каждого центра свой):
  ```sql
  UPDATE tenant_counter SET value = value + 1
  WHERE tenant_id = :tenantId AND name = 'student_number'
  RETURNING value;
  ```
- **Лимиты попыток и подобные инварианты** — уникальным индексом (например `(tenant_id, assessment_id, student_id, attempt_number)`), а не проверкой `count()` в транзакции: при READ COMMITTED она гонку не ловит (находка 3.4 аудита).
- **Архивирование вместо глобального soft-delete.** Явный статус (`ACTIVE` / `ARCHIVED`) на сущностях, где он имеет смысл. Магический фильтр «удалённое скрыто везде» не использовать: в best-direction он требовал помнить про отдельный клиент без фильтра в корзине, уникальности и окончательном удалении, и ошибки из-за этого уже случались.
- **Миграции совместимы в обе стороны на время деплоя** (expand → migrate → contract): сначала добавляется новое, затем переносится код, затем в отдельном релизе удаляется старое.

## 13. Тестирование

**Инструменты:** JUnit 5, Testcontainers с Postgres той же версии, что в проде, ArchUnit, тесты Spring Modulith. Все интеграционные тесты — на настоящей БД с настоящими RLS-политиками.

**Обязательные с первого дня, до бизнес-функций:**

1. **Межарендаторная утечка по всем эндпоинтам.** Создаются арендаторы A и B с данными. Тест получает все маршруты из `RequestMappingHandlerMapping` и для каждого маршрута с идентификатором в пути выполняет запрос от пользователя A к объекту B. Ожидается 404. Новый эндпоинт попадает под тест автоматически, без правки теста.
2. **Запрет по умолчанию** — ArchUnit, раздел 5.4.
3. **Все сущности центра наследуют `TenantScopedEntity`** — ArchUnit, раздел 4.2.
4. **RLS** — четыре теста из раздела 4.3.
5. **Границы модулей** — `ApplicationModules.of(CrmApplication.class).verify()`.
6. **Матрица прав** для каждого модуля: маршрут × право → ожидаемый статус.

**Доменные тесты** — для billing, attendance, payments, enrollment; переносят проверенные сценарии из best-direction.

**CI не деплоит без зелёных тестов.**

## 14. Инфраструктура

### 14.1. Старт

- **VPS 4 ГБ RAM минимум.** JVM с Postgres, Caddy и MinIO не поместятся в 1 ГБ, на котором сейчас работает best-direction.
- Docker Compose: `caddy`, `app` (Spring Boot), `db` (Postgres), `minio`. Лимиты памяти заданы явно, у JVM — `-XX:MaxRAMPercentage`.
- **Все переменные окружения перечислены в `environment:` каждого сервиса.** Docker Compose не пробрасывает `.env` в контейнер сам; в best-direction именно так в проде молча не заработали Piston и Redis.
- Пароли без фолбэков: `${DB_PASSWORD:?}`.
- Caddy: TLS, HSTS, CSP для SPA, `/api/*` → `app`, остальное → статика SPA.

**Локализация данных.** Перед запуском проверить с юристом требования законодательства Узбекистана о персональных данных — в частности, требование хранить персональные данные граждан на серверах, физически расположенных в стране. От ответа зависит выбор хостинга.

### 14.2. Бэкапы — до первого клиента

- Непрерывное архивирование WAL + ежедневный базовый бэкап (pgBackRest или аналог), копия за пределами сервера.
- Бэкап MinIO за пределами сервера.
- **Ежемесячная проверка восстановления** на отдельной машине. Бэкап, из которого ни разу не восстанавливали, не считается бэкапом.

### 14.3. Наблюдаемость

- Actuator: health, метрики.
- Структурные JSON-логи с `tenant_id`, `user_id`, `request_id` в каждой строке.
- Внешний мониторинг доступности с оповещением в Telegram.
- Оповещения: ошибки 5xx, незавершённые события outbox старше N минут, упавшие задачи, место на диске, отставание бэкапа.

### 14.4. CI/CD

1. Сборка и все тесты (раздел 13), включая сборку фронтенда.
2. Образ с тегом коммита.
3. Деплой только из `main`, только после зелёных тестов, с `concurrency`-группой — деплои не идут параллельно.
4. Бэкап перед миграцией.
5. Проверка health после деплоя; при провале — откат на предыдущий тег.

## 17. Чего не делать

- **Микросервисы.** Один разработчик, один модульный монолит. Выделять сервис только при измеримой причине.
- **Kubernetes.** Docker Compose достаточно до многих сотен центров.
- **Схема или БД на арендатора на старте** — раздел 4.1.
- **Keycloak на старте** — раздел 5.2.
- **Stateless JWT для сессий пользователей и токены в `localStorage`.**
- **Проверки по названию роли в коде.** Только права.
- **Глобальный магический soft-delete.**
- **GraphQL.** REST + OpenAPI проще защищать и генерировать клиент.
- **Event sourcing для всей системы.** Журнал начислений и оплат только дописывается — этого достаточно.
- **Бизнес-логика во фронтенде.** Ни одного правила, которое сервер не проверяет сам.
